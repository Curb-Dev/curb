================================================================================
DEPTH - WHAT A TRADE ACTUALLY COSTS, MEASURED
================================================================================

WHAT THIS ANSWERS
  ROADMAP Phase 0 B: both directions, real sizes, total cost after fees rather
  than slippage alone. It is in two halves because they are two different kinds
  of fact:

    THE CONVERSION      NVDAc against USDC and against ETH, on somebody else's
                        liquidity. Depends on the chain, so it is measured at a
                        named block and goes stale.
    OUR OWN POOL        a graduated CURB pool. Depends on parameters WE pick,
                        not on the chain, so it does not go stale - it changes
                        when we change the threshold or the tax.

WHAT IT DOES NOT ANSWER
  Nothing here decides anything. "A trade of this size costs this much" is a
  measurement; WHICH COST IS ACCEPTABLE is a product decision, it has not been
  made, and the candidates at the end are candidates.

--------------------------------------------------------------------------------
ONE DEFINITION OF COST, AND THE OTHER ONE NAMED WHEREVER IT APPEARS
--------------------------------------------------------------------------------
  SHORTFALL      cost = 1 - returned / expected-at-mid
                 "this share of my money did not arrive". Same on a buy and a
                 sell, never above 100%. EVERY TABLE BELOW USES THIS.
  PRICE OVER MID cost = paid / mid - 1
                 "the price I got was this much worse than mid". Only the
                 costLimit tests use it, because "a 3% limit" reads naturally
                 as a price limit. Wherever it appears it says so in the label.

  THEY ARE NOT THE SAME NUMBER: the second is the first divided by (1 - the
  first). 48 bps against 48 bps is a rounding difference; 7745 against 7745 is a
  factor of four.

  THE FIRST VERSION OF THIS FILE MIXED THEM, and not only between the two
  halves - the pool table's BUY leg was price-over-mid while its own SELL leg
  was already the shortfall, in one table, under one "bps" heading. Its
  headline conclusion was read straight off that gap. See CORRECTIONS at the
  end; the tests now emit both, each named.

HOW TO REPRODUCE
  bash script/b20/measure-depth.sh          the conversion half, own fork,
                                            read-only, prints its own block
  B20_FORK=true base-forge test --match-path "test/fork/B20Graduation*" \
      --match-test "depth_threshold|costLimit" --fork-url <pinned node> -vv
  bash script/b20/mutate-depth-lock.sh    does the port lock actually hold?
  bash script/b20/faultinject-depth.sh    does a broken RPC ever become a
                                          number? (needs a node on 8553)
  base-forge build script/b20/SwapDeltaProbe.sol    the measurement needs
                                          this artifact and refuses without it

  DO NOT run base-forge test with --fork-url and no --match-path. It does not
  complete in this environment; script/b20/test-all.sh exists for that reason,
  and this work re-made the mistake once.
  WHAT WAS OBSERVED: 20 minutes elapsed, 31 seconds of CPU, no output, the
  process alive, the node answering. WHAT WAS NOT: a cause. "blocked on
  upstream RPC" was written here as if it had been established; it had not.
  Low CPU with no progress is consistent with waiting on the network AND with
  several other things, and nothing measured which. test-all.sh's own header
  already says the cause was never measured - the same discipline belongs here.
  Use test-all.sh.

1.4  WHAT A TRADE COSTS at the sizes Phase 0 B names
--------------------------------------------------------------------------------
  THE COST IS OF THE TRADE THAT ACTUALLY HAPPENED:
      cost = 1 - received / (mid value of the input REALLY SPENT)
  Both sides come from the same probe call, and the quoter is a cross-check
  that STOPS the row if it disagrees. Includes the 30 bps LP fee; our own tax
  is zero on these legs.

  ON A PARTIAL FILL THE UNSPENT INPUT STAYS WITH THE TRADER, so it is not a
  cost. "shortfall" is how far the output falls below the mid value of the
  WHOLE offer, and it is NOT a trade cost - it is printed only so the two
  cannot be confused again.

    notional   NVDAc->USDC    USDC->NVDAc    NVDAc->ETH        ETH->NVDAc
    $50           32 bps         32 bps         31 bps           31 bps
    $100          34 bps         34 bps         33 bps           33 bps
    $500          56 bps         48 bps         44 bps           44 bps
    $1,000        87 bps         66 bps         58 bps           58 bps
    $5,000       369 bps        294 bps        191 bps          166 bps
    $10,000      791 bps        639 bps    564 bps / 91.0%      304 bps
    $50,000     7833 bps       7688 bps    564 bps / 18.2%   513 bps / 24.6%

  THE CELLS WITH A PERCENTAGE ARE PARTIAL FILLS. NVDAc->ETH at $50,000 spends
  18.2% of the offer - a $9,102 trade - and THAT trade costs 564 bps. The
  $10,000 row is the same swap, so it costs the same. The shortfall against the
  whole offer is 8282 bps and 1412 bps respectively, and an earlier version of
  this file printed THOSE as the cost, charging the trader for money that never
  left their wallet.

  THE 100% ROWS AT $50,000 ARE STILL BAD. The input is consumed in full and 77%
  of the value does not come back.

  THE USDC POOL IS NOT SIMPLY BETTER - IT IS WORSE WHEREVER BOTH FILL FULLY.
      selling NVDAc   56 / 87 / 369 bps through USDC
                      44 / 58 / 191 bps through ETH     at $500 / $1k / $5k
      buying NVDAc    48 / 66 / 294 bps through USDC
                      44 / 58 / 166 bps through ETH     at $500 / $1k / $5k
  A higher balance does not mean a better price at any given size.

--------------------------------------------------------------------------------
  The largest notional that is BOTH fully consumed AND under a stated cost.
  Both halves come from ONE probe call - the measured spend and the measured
  output - and a quoter that disagrees with it abandons the search rather than
  supplying a second opinion nobody reads.

    leg             under 50 bps   under 100 bps   under 300 bps
    NVDAc -> USDC        $388          $1,189          $4,052
    USDC  -> NVDAc       $562          $1,810          $5,090
    NVDAc -> ETH         $713          $2,434          $7,188
    ETH   -> NVDAc       $725          $2,554          $9,875

  SO: about $1,200-$2,600 moves at under 1%, and about $4,000-$9,900 at under
  3%. The most any single trade was seen to return is ~$8,600-$11,700 depending

================================================================================
  MEASURED ON THE PINNED FORK, block 51171034, hash 0x7bfea0b6...b35f. The
  pinned block is correct here and is NOT a staleness problem: a graduated

  THE TAX IN THIS TABLE IS 3% - TOTAL_TAX_BPS, the middle of the 1-5% band -

  At a 3% tax the fee part is 329 bps, so that comment understated every row by
  about 200 bps of pure fee.

  BOTH DIRECTIONS, SAME ABSOLUTE SIZE, THREE THRESHOLDS, ONE DEFINITION
  (shortfall; the price-over-mid figure for the same buy is in brackets)

    threshold   size       buy              sell
    2 NVDAc     0.05       557 bps  ( 590)   564 bps
                0.25      1372 bps  (1590)  1400 bps
                1.00      3481 bps  (5340)  3546 bps
    4 NVDAc     0.05       444 bps  ( 465)   448 bps
                0.25       880 bps  ( 965)   896 bps
                1.00      2212 bps  (2840)  2258 bps
    8 NVDAc     0.05       387 bps  ( 402)   388 bps
                0.25       612 bps  ( 652)   621 bps
                1.00      1372 bps  (1590)  1400 bps

  A SELL COSTS SLIGHTLY MORE THAN A BUY OF THE SAME SIZE, at every row.
  The previous version said the opposite, and said it "consistently". It was
  comparing the bracketed column against the sell column - two definitions. Its
  EXPLANATION was right and its conclusion was the wrong way round: the tax
  comes off a buy's input BEFORE the pool sees it, so less of the trade moves
  the price, while a sell's whole position hits the pool and the tax comes off
  the output afterwards. That mechanism makes the buy cheaper, which is what
  the corrected numbers show.

  THE CLOSED FORM, EXACT under this definition, not an approximation
      k = (1 - T)(1 - f)                 T = tax, f = LP fee
      buy   cost = 1 - k / (1 + (S/Q) * k)
      sell  cost = 1 - k / (1 + (S/Q) * (1 - f))
    where S is the trade and Q the pool's quote depth. It reproduces all nine
    buy rows and all nine sell rows above to the basis point - 3481 and 3546 at
    2 NVDAc, 387 and 388 at 8 - and both costLimit depths as well: it gives
    289.4 where the 60 NVDAc test measured 289, and 465.8 where the 28 NVDAc
    test measured 465. TWENTY POINTS, NO MISMATCHES, so the model is checked
    against the chain rather than fitted to it - and the inverse below is
    algebra on a checked formula, not a second measurement.

    THE FIRST TERM IS A FLOOR THAT DEPTH CANNOT TOUCH: 1 - (1-T)(1-f).
      T = 1%   129.7 bps     T = 3%   329.1 bps     T = 5%   528.5 bps
    A launch charging 5% can never cost a trader under 5.3%, at any depth.

  SOLVED FOR DEPTH, which is what a threshold decision needs
      Q  =  S * k * (1 - C) / (k - (1 - C))        C = the cost you will accept
    For a 1 NVDAc trade at a 1% tax: 56.22 NVDAc for a 3% shortfall, 25.32 for 5%.

  THE costLimit TESTS ASSERT ON PRICE-OVER-MID, NOT ON THIS, and they are at
  the band's FLOOR - a 1% tax. Read together:
      depth 60 NVDAc  ->  298 bps price over mid = 289 bps shortfall
      depth 59        ->  300 bps                  (misses a 3% price limit)
      depth 59.2      ->  300 bps rounded, over it unrounded
      depth 28 NVDAc  ->  488 bps price over mid = 465 bps shortfall
      depth 27        ->  501 bps                  (misses a 5% price limit)
    60 and 28 are the depths a 3% and a 5% PRICE limit need. Under the
    shortfall definition the same limits need 56.22 and 25.32. Neither is a
    chosen product parameter.

  AND THE TWO HALVES MEET HERE, NARROWLY
    1 NVDAc is 211.78 USD at the block in section 1, so a 60 NVDAc threshold is
    about 12,700 USD of quote depth. Compare that with 1.3: the most NVDAc a
    single trade was OBSERVED to return is 54.59 from the USDC pool (~11,560
    USD) or 55.03 from the WETH pool (~11,655 USD), and under 1% of cost about
    1,200-2,600 USD moves at a time. Those ceilings are the highest seen over
    the amounts tried, not proven maxima.
    WHAT THAT DOES AND DOES NOT MEAN. IF the buyers filling a launch convert
    into NVDAc through these two pools, then one launch needs more NVDAc than
    either pool can produce in a single trade, and two launches filling at once
    compete for the same liquidity. THEY ARE NOT OBLIGED TO. NVDAc can be held
    already, bought at Coinbase, bridged in, or sourced from a venue this
    measurement never looked at. This is a constraint on ONE ROUTE, measured;
    it is not a constraint on the product, and no change to our code moves it
    either way.

3. THE DECISION TABLE - measured, and still not a decision
================================================================================
Nothing in the code has been set to any of this. No product parameter has been
chosen as part of this work.

WHAT A THRESHOLD DECIDES, precisely: the quote depth Q of the graduated pool,
and through that the cost of a trade of size S at the launch's tax T. The tax
is the creator's, between 1% and 5%.

THE FLOOR NO DEPTH CAN GET UNDER IS THE TAX AND THE LP FEE TOGETHER, as price
impact goes to zero: 1 - (1-T)(1-f), with f the pool's tier. At the 0.30% tier
that is 129.7 bps at a 1% tax, 329.1 at 3% and 528.5 at 5%. IT IS NOT THE TAX
ALONE - the tax alone would be 100, 300 and 500 - and the conversion leg does
not add to it either, it composes. A threshold cannot be chosen without both
the tax and the tier.

--------------------------------------------------------------------------------
3.1  THE TWO LEGS, AND WHY THEY ARE PRINTED APART
--------------------------------------------------------------------------------
  EXTERNAL CONVERSION COST. Somebody arriving with ETH must trade it for NVDAc
  on somebody else's liquidity, and selling out means trading back. BOTH
  DIRECTIONS ARE MEASURED IN ONE RUN AT BLOCK 51359669, because a claim that
  one direction costs a few bps more than the other cannot rest on two
  measurements taken minutes apart.
  OUR OWN POOL'S COST. The launch token against NVDAc. Measured on the pinned
  fork at block 51171034, and it follows from OUR parameters, not the chain's.

  BOTH ARE THE USER'S. A trader pressing our ETH button pays the conversion as
  part of what that button costs them, whoever collects it. An earlier version
  of this section called the conversion "not a cost of our product", which is
  true about where the money goes and false about what the user pays. The split
  that matters is WHO SETS IT: we set the pool leg, and the conversion is the
  chain's. Somebody who already holds NVDAc pays only the pool leg.

  THESE ARE STILL TWO MEASUREMENTS AT TWO BLOCKS - the conversions at 51359669
  and our pool on the pinned fork. There is no end-to-end measurement of
  ETH -> NVDAc -> launch token or of the way back, and 3.5 says so where the
  totals are.

3.4  THE LP TIER - MEASURED AT BOTH SETTINGS, not subtracted
--------------------------------------------------------------------------------
  AN EARLIER VERSION OF THIS SECTION SAID "0.05% would take about 25 bps off
  every cell". IT IS NOT A CONSTANT, and measuring both tiers at the same sizes
  shows why: 25 bps is the difference in the FEE, which is nearly all of what a
  tiny trade pays and a shrinking part of what a large one pays. A lower fee
  also lets MORE of the input reach the pool, which moves the price further, so
  the two effects work against each other.

  0.30% -> 0.05%, a buy, in bps (87 cells measured across both directions)
    size       tax      Q=10           Q=20           Q=60
    $50        1%    354 -> 330     243 -> 219     167 -> 143
               5%    735 -> 712     633 -> 610     563 -> 540
    $100       1%    569 -> 546     354 -> 330     205 -> 181
               5%    933 -> 912     735 -> 712     598 -> 575
    $500       1%   1995 -> 1978   1159 -> 1139    498 -> 475
               5%   2259 -> 2243   1480 -> 1461    868 -> 846
    $1,000     1%   3267 -> 3255   1995 -> 1978    841 -> 819
               5%   3455 -> 3444   2259 -> 2243   1185 -> 1164
    $5,000     1%   7036 -> 7033   5441 -> 5436   2890 -> 2877
               5%   7073 -> 7070   5528 -> 5522   3100 -> 3087

  THE SAVING IS 24 bps AT THE SMALLEST TRADES AND 2 bps AT THE LARGEST.
  Across all 87 cells it runs 2 to 24 bps on a buy and 5 to 25 on a sell. It is
  worth most exactly where the total is already smallest, and nearly nothing
  where the total is unusable - so the tier decides the RETAIL experience and
  cannot rescue a thin pool.

  AND IT IS NOT FREE. Our LP is the LOCKED position and its fees go to the
  creator, so a lower tier moves that 24 bps from the trader to nobody: the
  trader pays less and the creator earns less. That is a transfer, not an
  improvement, and choosing it belongs with D1.

--------------------------------------------------------------------------------
3.5  BOTH LEGS TOGETHER - ARITHMETIC, NOT A MEASUREMENT
--------------------------------------------------------------------------------
  composed = 1 - (1 - legA)(1 - legB). It is NOT the two added: the second leg
  only acts on what survived the first. The cells below are written
  "legA / legB / composed" with slashes for that reason - an earlier version
  wrote them with a plus sign, which contradicted the formula above it.

  EACH LEG IS MEASURED AT THE AMOUNT THAT LEG ACTUALLY TRADES.
    BUYING IN   the conversion trades the user's $X and returns a NET NVDAc
                amount; our pool is then measured AT THAT NET, not at the
                nominal $X. The net amounts come from the entry table and are
                in the fork suite as NETE_* and NETU_*.
    SELLING OUT our pool trades the nominal size and returns a NET NVDAc
                amount; the conversion is then measured AT THAT NET.
  An earlier version measured the sell this way and the buy at the nominal,
  which overstated every buy - by 31 to 41 bps at $5,000 - and then compared
  the two. See correction 19.

4. CORRECTIONS - TWO ROUNDS OF THEM
================================================================================
Kept rather than quietly overwritten, because each one is a way a measurement
can be right and still say something false.
  1-7    the first round: what the write-up claimed that the numbers did not
         support.
  8-11   the second: what the measuring TOOL did - reading its own failures
         as data, and naming a probe as an enumeration.
  12-15  the third: an ESTIMATE printed as a measurement, a partial fill
         called a refusal, a finite sweep stated as a universal, and a
         search that never checked the trade it was sizing would fill.
  16-18  the fourth: a partial fill's cost charged on money the trader still
         had, a cost and a fill taken from two simulations that were never
         compared, and an RPC failure ending in a stack trace.
  19-20  the fifth: a conclusion about DIRECTION drawn by comparing two
         differently-computed totals, when this file had already written
         down that one of them was overstated by more than the difference
         being claimed - and a composed cell printed with a plus sign over
         a multiplicative formula.
  21-23  the sixth, all in prose rather than in a table: a median trade
         size invented out of nothing, a cost floor quoted as if the LP
         tier were already decided when it is one of the open choices, and
         two readings of the scenario that claimed more than its cells do.
  These get worse down the list. A wrong write-up can be re-read; a tool that
  launders an inference into a measurement produces new wrong write-ups.

  1. THE LOCK. script/b20/measure-depth.sh installed its EXIT trap before it
     claimed the port and then ran an unconditional rm -rf on the lock, so a
     run REFUSED because somebody else held the claim deleted that claim on the
     way out. Same bug stop-node.sh was fixed for twice.
     MUTATION-TESTED, and the first result was not the expected one.
     script/b20/mutate-depth-lock.sh deletes each guard in turn:
       - deleting the HELD flag changed NOTHING against a foreign lock. The
         owner comparison alone already refuses. HELD is only reachable when a
         STALE lock carries the same id this run computes for itself - which
         "depth-$$" allowed, because pids get reused. The id now carries the
         process start time as well, the way start-node.sh already did, and the
         harness forces the case by pinning the id: guard deleted, the lock is
         destroyed; guard present, it survives.
       - deleting the owner comparison DOES break it, against a lock this run
         took and somebody else then overwrote.
       - and the lock is still released on a clean exit, or the next run could
         never start.

  2. TWO COST DEFINITIONS UNDER ONE HEADING - and inside a single table, where
     the buy leg was price-over-mid and the sell leg was the shortfall. The
     table's headline, "a buy costs more than a sell, consistently", was that
     gap and nothing else. Under one definition the sell is dearer, every row.

  3. "ALL OF NVDAc'S UNISWAP v3 DEPTH ON BASE IS ABOUT 42,000 USD" was wrong
     twice over: the figure is the pools' combined BALANCE, not a trade depth -
     one trade can extract at most ~12,800 USD - and the scan behind it covered
     four of seven enabled tiers and two of seven candidate quote tokens.

  4. THE $10,000 NVDAc->ETH CELL never measured a $10,000 trade. QuoterV2 does
     not check that an exact-input swap consumed its input; it reports whatever
     came out when the swap stopped at the price bound. 78.7% of that input was
     spent. Every cell now carries the share actually spent, from a second
     quote, cross-checked against the returned sqrtPrice.

  5. "THE USDC POOL IS DEEPER SO IT IS BETTER" - the table itself showed the
     WETH route cheaper for several sizes then, and the re-measurement makes it
     stronger: the WETH pool is cheaper or exactly equal at EVERY size where
     both pools fill the whole input, while holding less.

  6. THE OWN-POOL TABLE NEVER STATED ITS TAX (3%) and was missing five of its
     nine rows. Both fixed; the tax and the LP fee are now emitted by the test
     itself rather than left in a constant a reader has to go and find.

  7. "FILLING A LAUNCH IN $500 PIECES COSTS ABOUT 48 BPS EACH" - every quote in
     section 1 is read from the same starting state, so they are alternatives,
     not a sequence. Doing them one after another costs more each time.

  8. RPC FAILURES WERE BEING READ AS DATA, in four places. Every call ran as
     `base-cast call ... 2>/dev/null` and the empty output was taken for an
     answer: a failed tier query became "that tier is not enabled", a failed
     symbol() became "not a token", a failed getPool became "no pool".
     THE DANGEROUS ONE WAS THE COST-LIMIT SEARCH. A failed quote became zero
     output, zero output reads as infinite cost, and infinite cost drove the
     bisection DOWNWARDS - so a network fault produced a low depth figure that
     looked entirely plausible.
     EVERY CALL NOW HAS THREE OUTCOMES, not two: answered, REVERTED (which is
     data - a pool that does not exist, a token with no symbol), or FAILED
     (transport, timeout, an unrecognised error - which is ours and is never
     data). Only "execution reverted" counts as a revert; anything unrecognised
     is treated as our failure, because the safe direction is to report less.
     A structural read that fails stops the run; a ladder row that fails prints
     as failed; a search that fails is ABANDONED and prints no number; and the
     tool exits non-zero either way.
     TESTED, NOT ASSERTED. script/b20/faultinject-depth.sh puts a proxy in
     front of the fork and breaks exactly what it is told to break - a dead
     node, the tier probe, a balance read, a batch, and quotes failing every
     fifth call partway through. Eight cases.
     AND MUTATION-TESTED, which is the part that matters. Put the old
     behaviour back - a failed quote read as zero output - and under the same
     intermittent fault the search stops abandoning and starts answering:
         true            420 / 1,231 / 4,103    (NVDAc->USDC, 50/100/300 bps)
         old behaviour   419 / 1,159 / 3,024
         true            601 / 2,126 / 8,971    (ETH->NVDAc)
         old behaviour   579 / 1,511 / 8,839
     Plausible, quiet, and understating depth by up to 37%. That is what the
     rule is for.

  9. THE EXACT-OUTPUT QUOTE IS NOT THE SAME SWAP, and the "78.7% of the input
     was really spent" figure leaned on it as though it were. It is a second
     simulation of a different question - "what input buys exactly this
     output" - and rounding and the path the price takes need not agree.
     WHAT IS USED NOW: a swap that did not end on QuoterV2's price bound
     stopped because its input ran out, so "consumed in full" is read off the
     very call being reported. For the rows that DID hit the bound, the amount
     consumed is the bisected input bound - the same call, the same state - and
     the exact-output quote is kept as a cross-check, labelled as one. On the
     two WETH legs it agrees to 0.0000%; on the USDC legs it is not comparable
     and the tool says so instead of reporting a disagreement.
     QuoterV2 does not return the input an exact-input swap consumed, so no
     single call yields it. That limit is stated rather than worked around.

 10. "THE LARGEST TRADE THE POOL WILL ACCEPT" WAS NOT MEASURED, it was one
     absurd quote plus an exact-output round trip. Measuring it showed the two
     pools do not even have the same KIND of limit: the WETH pool stops taking
     input partway, while the USDC pool spent every amount that could be put to
     it and stopped increasing its output. The old table's "max input it
     accepts: 46,601 NVDAc (~9.87M USD)" was neither pool's behaviour.
     THE WORDING OF THAT FIX WAS ALSO WRONG, twice, and 13 and 14 below are
     what it took to say it correctly.

 11. "THE ENABLED FEE TIERS" WAS 12 HAND-WRITTEN CANDIDATES. It is now a
     probed domain of 2,907 values, named as a probe. The complete answer is
     the factory's FeeAmountEnabled logs and this upstream refuses to serve
     them - eth_getLogs is capped at a 2,000-block range - so the limit is
     recorded with the refusal rather than left implied. Both scans find the
     same seven tiers; the difference is what may honestly be claimed.

 12. THE CONSUMED SHARE WAS AN ESTIMATE PRINTED AS A MEASUREMENT. Bisecting
     QuoterV2's price bound asks many simulations of DIFFERENT amounts from the
     same state and infers a boundary. It is a good estimate of a boundary and
     it is not the input the swap in front of you spent - which QuoterV2 does
     not return at all.
     script/b20/SwapDeltaProbe.sol reads the pool's own returned deltas for
     THAT swap. Its bytecode is installed for the duration of one eth_call by
     that call's state override, at the v4 PoolManager - an address that
     already holds NVDAc, WETH and USDC, because NVDAc cannot be minted into a
     fresh address. Nothing is mined and no transaction exists. The callback
     pays for real, which is what makes it evidence: an unpaid pool reverts.
     THE ESTIMATE TURNED OUT TO BE RIGHT, to 0.0000% on both WETH legs, and the
     exact-output quote agrees as well. That is worth knowing and it is not a
     reason to have printed it as a measurement.
     THE PROBE IS ASKED FOR THE MOST THE HOST CAN PAY, so a revert means the
     POOL stopped, never that funding ran out.

 13. "THE POOL REFUSES AN INPUT OVER ~36.6 NVDAc" DESCRIBED A REVERT. Nothing
     reverts. The swap fills PARTIALLY: the call succeeds, the pool takes what
     it can and pays for it, and the remaining input is simply never spent. A
     partial fill and a failed transaction are different things for anyone
     building on top of this, so the word was wrong and not just loose.

 14. "THE USDC POOL CONSUMES ANY INPUT HOWEVER LARGE" WENT PAST THE SWEEP. The
     code tries a finite range; not finding a bound below 2^200 is not a proof
     that none exists, and a plateau observed over the amounts tried is not a
     proven capacity. Both now read as what they are: "every amount tried was
     consumed in full, up to X - the most the probe could fund" and "the
     highest output OBSERVED over inputs up to Y".

 15. AND THE COST-LIMIT SEARCH DID NOT REQUIRE FULL CONSUMPTION. It compared
     cost alone, so a partially filled quote could answer "this whole amount
     trades at this cost" for a size the pool only partly fills. The condition
     now includes the measured spend. On this run it moved the ETH legs - the
     $50/100/300 bps figures went from 601/1,965/5,791 to 759/2,449/6,965 -
     though that is across different blocks, so it is not a clean before/after
     of the fix alone.

 16. THE COST OF A PARTIAL FILL WAS CHARGED ON MONEY THE TRADER STILL HAD.
     cost = 1 - out/expected, with `expected` the mid value of the WHOLE offer.
     On a partial fill the unspent input never leaves the wallet, so counting
     it as a shortfall reports a loss nobody took. AT THE BLOCK IN SECTION 1,
     both numbers are on the table: the $50,000 NVDAc->ETH row's shortfall is
     8282 bps, and the trade that actually happened there - $9,102 of NVDAc -
     costs 564 bps. A factor of fifteen, in the direction that makes the venue
     look unusable. (The run before this one printed 8246 as the cost; that is
     the same mistake at a different block, and the two are not compared here
     because they are not the same state.)
     THE COST IS NOW AGAINST THE INPUT REALLY SPENT, and the fill is a separate
     column. The old figure is still printed, as "shortfall", explicitly not a
     trade cost, so the two cannot be merged again by accident.
     AND THE $10,000 AND $50,000 ETH ROWS NOW READ THE SAME 564 bps, which is
     right: both fill to the same boundary, so both are the same swap.

 17. THE COST AND THE FILL CAME FROM DIFFERENT SIMULATIONS. The search took the
     cost from the quoter and the fill from the probe and threw the probe's
     output away (`spent, _`), so the answer was assembled from two runs of the
     same swap that were never compared - and a disagreement could not have
     been noticed. Both halves come from one probe call now, and a quoter that
     disagrees ABANDONS the search instead of being ignored.
     TESTED: script/b20/faultproxy.py gained a `skew` mode that forwards the
     call and then changes the answer by one unit. Nothing errors; the two
     simulations simply stop agreeing. The tool prints DISAGREE and produces no
     bound. Ten fault cases now.

 18. AND ONE IN THE ORCHESTRATION, found by this work rather than reviewed for.
     measure-depth.sh read the block hash with `base-cast block N --json`,
     which asks for the FULL block; the public endpoint answered "backend
     response too large", the hash came back empty, and the run died on a
     python traceback. Right outcome, wrong mechanism - an RPC problem has to
     end in a clear statement that the measurement did not happen, not in a
     stack trace. It fetches the header without transactions now and validates
     the hash before using it.

 19. "THE SELL IS 10-12 bps CHEAPER AT $5,000" WAS AN ARTIFACT OF COMPARING TWO
     DIFFERENT METHODS. The sell total composed our pool's cost with a
     conversion measured at the REAL net NVDAc the pool returned. The buy total
     composed the conversion with our pool's cost at the NOMINAL size - an
     amount the user never held, because the conversion had already taken 157
     bps out of it. This file said in the same section that the buy was
     therefore overstated by 31 to 41 bps at $5,000, and then compared the two
     anyway. The error was larger than the advantage being claimed.
     THE FIX IS TO MEASURE THE BUY THE SAME WAY. The entry leg's net NVDAc is
     measured (NETE_* and NETU_* in the fork suite) and our pool is run at
     those amounts.
     THE CONCLUSION REVERSES. In all 84 cells where both directions are
     measured the sell is 0 to 130 bps WORSE, and in none of them is it
     cheaper. It was not a small correction to a true statement; the statement
