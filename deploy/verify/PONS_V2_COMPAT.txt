================================================================================
CURB'S CURVE AGAINST THE PONS V2 CURVE 0x LISTS ON ROBINHOOD CHAIN
================================================================================
Date   : 18 October 2026
Asked  : does CURB's curve (src/vendor/PonsV2BondingCurve.sol, "vendored
         unmodified" from ponsdotdev/ponsfamily @ debbc21f) have the same
         external ABI and event signatures as the "Pons V2 bonding curve" 0x
         added as a Robinhood Chain source (docs.0x.org changelog, 31 July
         2026), and what differs around it?
Reached: the Robinhood Chain deployment itself - its public RPC answered,
         and Sourcify serves its verified sources. Blockscout's explorer for
         the chain answered with a Cloudflare challenge and was not used.
         0x's own integration is not public (SOURCES, at the end).


THE SHORT ANSWER
  THERE ARE TWO PONS V2 CURVES ON ROBINHOOD CHAIN, and 0x's changelog
  predates the second.
  - The FIRST GENERATION, live on 31 July, is CURB's curve: the same source
    apart from whitespace, and deployed runtime code identical byte for byte
    to $CURB's curve on Base once immutables and the metadata trailer are set
    aside. Same functions, events, errors and constructor.
  - The SECOND GENERATION, the factory Pons launches from today (created 3
    August), is a strict superset: every one of CURB's 39 functions, 11
    events and 22 errors is there unchanged, plus a snipe tax - 7 functions
    and 2 events CURB's curve does not have.
  Which of the two 0x routes today, and how it finds curves, is not public.
  What differs AROUND the curve - discovery, the quote asset, who holds the
  factory role, what the fee fields mean, the pool after graduation, and the
  chain - is listed below, and any of it is enough to keep an integration
  built for Pons from seeing CURB's launches unchanged.

2. THE CURVE ITSELF
--------------------------------------------------------------------------------
  SOURCE
    CURB's vendored file is upstream debbc21f's file with a provenance header
    added and one import path changed ("./libraries/PonsV2BondingCurveMath.sol"
    to "./PonsV2BondingCurveMath.sol"); diff says so and nothing more, apart
    from line endings (upstream's file is CRLF, with a trailing space on the
    import line).
    The first generation's curve source (Sourcify, factory 0x7E1E...) is
    debbc21f's, IDENTICAL apart from whitespace. Its interfaces, math
    library, token, buyback vault, deployer and hook are identical too; only
    its factory differs from debbc21f's.
    The second generation's curve (Sourcify, deployer 0x3711...) is
    debbc21f's plus the snipe tax and nothing else. debbc21f's own factory is
    the second generation's, whitespace apart: it calls exemptFromSnipeTax on
    a curve whose file at that commit has no such function. So the upstream
    commit pairs a second-generation factory with a first-generation curve
    and cannot build as one project as published. That is not CURB's
    concern: CURB vendors no Pons factory.

  ABI - both curve sources compiled with solc 0.8.30 for their ABI and
  method identifiers, then compared: functions by selector, state
  mutability and outputs; events by signature and indexed layout; errors
  and constructor by signature.

  THE DEPLOYED CODE
    $CURB's curve on Base (0x65CfF633dA0F81924242467D0C1404c6e0FEA7e4), the
    first-generation sample and this checkout's build of the vendored file
    are each 9,193 bytes, and are identical once the curve's 14 immutables
    (48 places, from the build's immutableReferences) are zeroed and the
    metadata trailer is cut. Not one byte differs. The trailers differ
    because the compiler (0.8.35 there, 0.8.30 here) and the source text (the
    header) do. $CURB's curve also equals the build with its trailer: a full
    match. This agrees with ADDRESSES.txt, where Sourcify already held a
    partial match for $CURB's curve "from another submission (solc 0.8.35,
    same runtime code)".
    The second-generation sample is 10,229 bytes. As a cross-check on the
    ABI comparison, the PUSH4 and PUSH32 constants in each deployed code were
    listed: all 39 shared selectors and all 11 shared event topics are in all
    three; the 7 snipe-tax selectors and the 2 snipe-tax topics are in the
    second-generation code only. (A constant in code is evidence, not proof,
    of a dispatch entry; the byte comparison above is the proof for the first
    generation.)

  BEHAVIOUR THAT CHANGED WITH THE SAME SIGNATURES (second generation)
    - CurveBuy's `fee` is the base fee PLUS any snipe tax; SnipeTaxCharged
      reports the tax separately. On CURB's curve and the first generation it
      is the base fee alone.
    - buy() prices with the snipe tax for the recipient (currentSnipeTaxBps,
      up to 9,900 bps in the launch second, zero after snipeTaxSeconds = 3)
      unless the recipient was exempted at launch. Outside that window the
      arithmetic is CURB's.
    - initialize() also reads snipeTaxStartBps() and snipeTaxSeconds() from
      its factory (IPonsV2SnipeTax). Internal to that deployment.


3. WHAT DIFFERS AROUND THE CURVE
--------------------------------------------------------------------------------
  THE CHAIN. 0x lists the source under Robinhood Chain (4663) alone. CURB is
  on Base (8453). Identical code is not routed until 0x adds it on Base.

  FINDING THE CURVES. Pons: one factory per generation, emitting
    TokenLaunched(address indexed token, address indexed curve,
      address indexed deployer, address pairToken, uint256 launchConfigId,
      uint256 graduationThreshold)       0x8d4aad4953d0ca700d468f3753aa14432d1b35b43ec6409f051fb6aa43a89607
  CURB emits no TokenLaunched. One LaunchRegistry for every asset,
  0x86e9a01F3959A96469051AE1a73D5C09b0BaC110, emits
    LaunchRegistered(address indexed launchToken, address indexed curve,
      address indexed beneficiary)       0x9fd8d418cff1010152155e55a312f5c2bbc5ce471864e9320174e12587793f0a
  and each of the fourteen CurbLaunchFactory contracts (ADDRESSES.txt)
  emits
    LaunchCreated(address indexed launchToken, address indexed curve,
      address indexed creator, uint256 supply, uint16 totalTaxBps)
                                         0x0280b3c18566ead1ee0d23f14d7732eeb3b1876056abe38c8548ceaee8ec5ef8
  registry.launchAt(i) and the registry's record give the curve and quote
  asset of each launch. An integration that finds curves through a Pons
  factory's address or its TokenLaunched topic finds none of CURB's.

  THE FACTORY ROLE. curve.factory() is the Pons factory there. On CURB it is
  the Graduator (0xA9865e07Ce4EC0cCf7A521B98640031285C92712): that role
  gates graduate(), and graduate() is what moves value
  (CurbLaunchFactory, where it builds the curve). The curve's auto-graduation
  calls IPonsV2LaunchFactoryGraduation(factory).graduate(token) on both, so
  on CURB the crossing buy calls the Graduator.

  THE QUOTE ASSET. A Pons ETH launch is native: pairToken() zero,
  isNativeQuote() true, buy() paid with msg.value equal to quoteIn (the
  second-generation sample). CURB has no native curve. Its ETH factory quotes
  WETH, 0x4200000000000000000000000000000000000006, as an ERC-20: approve,
  then buy() with no value. ETH in and out on CURB goes through CurbRouter
  0xEa20C3266229a01cd0f45D9c7921a45d5b359561 (buyWithEth, sellForEth), which
  converts on pairs other than WETH along a Uniswap v3 path through
  SwapRouter02. The
  other quote assets are CURB's fourteen on Base, not Pons's USDG, cbBTC and
  tokenized stocks on Robinhood Chain.

  WHAT THE FEE FIELDS MEAN - same code, other numbers.
    Pons (both samples): feeBps 100 is a base fee split by the frozen policy,
    protocolFeeShareBps 3000 to the protocol and, with buyback on,
    buybackBurnBps 5000 of the rest to its buyback vault, the remainder to
    the creator; creatorTaxBps is an extra creator tax (0 and 350 in the
    samples).
    CURB (CurbLaunchFactory, at curve creation): feeBps is the platform's
    share frozen at launch (50 at deployment, FeeHook.platformFeeBps());
    creatorTaxBps is the launch's tax minus that share, the tax being 100 to
    500 bps; protocolFeeShareBps 10000, so the whole base fee is the
    platform's; buybackBurnBps 0 and buybackEnabled false.
    So in CurveBuy and CurveSell, CURB's `fee` is the platform's part and
    `tax` the creator's; Pons's `fee` is the shared base fee (plus the snipe
    tax, second generation) and `tax` the creator tax. A quote computed from
    getReserves(), feeBps() and creatorTaxBps() is right on both, because
    the curve's arithmetic is the same - on the second generation only
    outside the snipe window, or with currentSnipeTaxBps added.

  THE FEE POLICY THE CURVE CALLS. The curve asks its feePolicy for
  feeSweepOperator() and pays into its feeEscrow and buybackVault through
  the same interfaces (ILaunchpadV2.sol, identical in CURB's vendored copy
  and the first generation's record). Pons's operator is an address its
  owner sets. CURB's FeePolicy.feeSweepOperator() returns the zero address:
  there is no such role, so only the curve's deployer() can call sweepFees
  (the creator, or the launch's holder distributor once sharing is switched
  on - Graduator.enableHolderSharing), and with buyback off
  buybackQuoteBalance stays zero, so no sweep needs an operator. Neither
  difference reaches a trade.

  AFTER GRADUATION the curve stops trading on both, and the market moves to
  a Uniswap v4 pool - another source for any aggregator, not the curve.
  Pons: its own PonsV2MemeHook (per its README, an afterSwap cut converted to
  the quote asset; LP fee 0 and tick spacing 200 per Bitquery's guide, not
  read from the chain here). CURB: FeeHook
  0xF85Ce05c2Ba8533d79f009fd3A3c8517aaBda0cC, LP fee 500 (0.05%), tick
  spacing 10 (DeployCurb POOL_FEE, TICK_SPACING), the launch's tax on buys
  and sells, exact-output swaps refused (ExactOutputNotSupported), and the
  position locked forever in a PositionLock. Whether an aggregator routes a
  v4 pool depends on its support for that particular hook.

  NO SNIPE TAX ON CURB. REFERENCE_ALIGNMENT.txt 4.1 records it as never
  decided; CURB's curve is the first generation's and has none.


4. WHAT THIS MEANS, AND WHAT IS NOT KNOWN
--------------------------------------------------------------------------------
  - Per curve, CURB is the Pons V2 first-generation contract, and a strict
    subset of the second generation's. Code that reads a curve through the
    39 shared functions and decodes the 11 shared events works on CURB's
    curves as written. Code that calls any of the seven snipe-tax functions
    reverts on them.
  - What an integration needs that is CURB's own: Base, discovery through
    the LaunchRegistry (or the factories' LaunchCreated), ERC-20 quote
    assets with WETH in place of native ETH, the fee fields' meaning above,
    and FeeHook pools after graduation.
  - NOT KNOWN: how 0x finds Pons curves (factory address, event topic, code
    hash or something else), whether it routes the first generation, the
    second or both today, and whether it would add a source on Base. 0x's
    integration code is not public, its changelog names the source and
    nothing more, and its API, which could list a chain's sources, takes an
    API key; none was used. Only 0x can answer these.


5. HOW IT WAS CHECKED
--------------------------------------------------------------------------------
  Read-only throughout: eth_chainId, eth_blockNumber, eth_getCode, eth_call,
  eth_getLogs and eth_getBlockByNumber against Robinhood Chain's public RPC
  and Base through Tenderly's keyless gateway, and GETs to Sourcify's API.
  The scripts were working files and are not committed; what they did:
  - Sourcify's records ("fields=all") of both Pons factories, the second
    generation's deployer and its hook: match level, compiler, deployment
    transaction and block, sources. The curve, interface, library, token,
    vault, deployer and factory sources written out and diffed against
    reference/ponsfamily (debbc21f) and src/vendor.
  - The ABI comparison: the vendored curve's standard JSON from base-forge
    (as in README.txt), the second generation's from its deployer's Sourcify
    record, both compiled with solc 0.8.30 for abi and methodIdentifiers.
    Event topics with cast keccak of each signature.
  - The code comparison: eth_getCode of the three curves; the vendored curve
    compiled in full for its immutableReferences; immutables zeroed and the
    trailer cut on all three before comparing.
  - Provenance: curve.factory(), factory.launchDeployer(), and the curve's
    trailer searched for in the deployer's code.
  - The TokenLaunched scan: eth_getLogs for its topic over blocks 19,441,846
    to 26,843,846 (26 July 00:30 UTC to just after the second factory's
    creation) in windows of 30,000 blocks, the largest the public RPC allows
    without an address; one window refused with 429 was asked again. And the
    second factory's own logs over its last 20,000 blocks.
